17. Do NOT store secrets in GitHub.

18. Do NOT log access tokens, refresh tokens, email bodies or private calendar bodies.

# PHASE 6 — EMAIL SYNC

Store the last successful sync.

Use a safety overlap window.

Do not rely only on a timestamp to prevent duplicates.

Deduplicate using Graph message ID.

A successful sync updates the checkpoint.

A failed or partial sync does NOT replace the last successful checkpoint.

A failed sync must not erase previously stored email data.

# PHASE 11 — RELIABILITY ENGINE

This is one of the most important parts of the application.

Create a common retrieval result structure:

```typescript
type RetrievalStatus =
  | "complete"
  | "partial"
  | "failed"
  | "unauthorized"
  | "rate_limited"
  | "source_unavailable";
```

Every retrieval must return:

```text
status
items
itemsChecked
pagesChecked
paginationComplete
startedAt
completedAt
error
```

Never return:

```text
[]
```

without a status explaining whether the empty result is genuine.

Example:

```json
{
  "status": "complete",
  "items": [],
  "itemsChecked": 0,
  "paginationComplete": true
}
```

is valid.

But:

```json
{
  "status": "partial",
  "items": [],
  "paginationComplete": false
}
```

means:

"we don't know whether there were additional messages."

# PHASE 12 — FAILURE RETENTION

Implement this rule:

If the current sync fails:

```text
DO NOT DELETE OLD DATA.
DO NOT RESET THE CHECKPOINT.
DO NOT REPORT ZERO RESULTS.
```

Instead:

```text
retain previous successful state
record failure
set current status = failed
```

The Morning Brief must be able to see that the latest scan failed.
